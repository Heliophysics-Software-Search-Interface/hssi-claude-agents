# HSSI Field Definitions

This skill is a router. The substance lives in one file per field:

```
fields/01-submitter.md … fields/33-logo.md      one file per field, uniform sections
sources/vocabulary-authority.md                  live API wins; the ONLY field → model endpoint table
sources/extraction-sources.md                    DataCite → Zenodo → SoMEF → PyHC cascade; literature routes
sources/form-structure.md                        the form's three sections, requirement levels, agreement
```

## How to use this skill

**Before you decide, validate, or patch Field N, Read `fields/NN-*.md`.** Paths are relative to this
skill's directory. A full extraction or refresh reads all 33 in order; a targeted update reads only the
fields in play. Each field file has the same sections, in this order:

| Section | What it answers |
|---|---|
| What it is | the form definition, sub-fields, allowed values (the `vocab:` block is regenerated by `update-api-spec`) |
| Why it exists | what a site user gets from the value |
| How it appears on the site | detail-page rendering, filter tab, search tier and field-search code |
| Rubric: include / exclude | numbered rules in stages (eligibility, selection, URL or row form, incumbents, verification); within a stage apply top to bottom and **stop at the first rule that fires**; a later stage, or a rule that says it fires on a value that passed an earlier rule, always runs — acceptance never skips a later check |
| Ask the user only when | the closed list of decision shapes that still need a human |
| Where to find it, and traps | sources in priority order, verification steps, known false positives |
| Payload and roundtrip notes | normalization, representation differences, PATCH quirks |
| Worked examples | short cases that illustrate the rules |
| Provenance | what is regenerated and when it was last verified |

**Deciding versus asking.** Decide and document autonomously whenever the field file covers the case.
Ask the user only (a) for a shape listed in that file's *Ask the user only when* section, or (b) when the
case is genuinely not covered by the written rules and is therefore ambiguous. "I am not confident" is
not (b); "no rule addresses this" is. Report every (b) question as a rubric gap so the field file can
be completed. Batch the questions you do have into one exchange.

## The governing test

Every rule in `fields/` derives from one question: **would someone using the HSSI website to find
software be glad this value is here, or find it out of place?** A value that only makes the record
tidier, more symmetrical, or easier to justify in the abstract, but that no site user benefits from,
does not belong. Four evidence rules follow from it and apply to every field:

1. **Evidence beats inference.** A value rests on something you read in the pinned source, a resolved
   identifier, or a fetched page — never on what a project of this kind usually does.
2. **A categorical claim needs a falsifying check.** "Verbatim", "the only", "no X anywhere" are the
   claims most often wrong; test them against the source before writing them.
3. **Prefer the project's own wording and spelling** for names, descriptions, and people; a stylistic
   alternative is not fresh metadata.
4. **An evidenced-empty value is legitimate; an unexamined blank is not.** Record why a field is empty.
