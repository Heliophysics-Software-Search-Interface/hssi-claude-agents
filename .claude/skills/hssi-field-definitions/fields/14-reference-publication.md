# Field 14 — Reference Publication

**Level:** OPTIONAL · **API:** `referencePublication` · **Change class:** static
**Vocabulary:** free text / no controlled list
**Filter tab:** none · **Free-text search tier:** T4.3 (name) · **Field-search code:** `reference_publication`, `publication`

## What it is

**Type:** DataCite DOI

**What it is:** The DOI for the publication describing the software, sometimes used as the preferred citation for the software in addition to the version-specific citation to the code itself.

**How to fill it:** Enter the DOI for the publication describing the software (e.g., a JOSS paper).

One URL: **the one paper the project asks users to cite for the software.** Written as the paper's
own DOI, `https://doi.org/<doi>`; for a qualifying paper with no DOI, its ADS abstract permalink
(`https://ui.adsabs.harvard.edu/abs/<bibcode>/abstract`) or arXiv abstract page. Other publications
about or using the software belong in Field 27.

## Why it exists

It tells a visitor which paper to cite when they use the software, next to the software's own
citation from Field 2. The page presents it as *the* publication for the software, so a paper that
only describes the underlying method, a different package, or a poster overstates what it is and
sends citations to the wrong work. When the project does ask for a paper and the field is empty,
the visitor loses the project's own citation guidance.

## How it appears on the site

- **Action button:** a "Publication" button in the page header links to the stored URL.
- **Reference Publication section:** a link whose text is the related item's name, or the raw URL
  when the name is `UNKNOWN`. Items created through the API store the URL as their name, so the link
  text is normally the URL itself.
- **Citation block:** the "Cite Me" button and Citation section also appear for a Field 14 URL. A
  "Reference Publication" citation is generated by `doi.org` content negotiation only when the value
  begins `https://doi.org/`; a non-DOI URL gets no generated citation. With both a Field 2 DOI and a
  Field 14 DOI, both citations show with a notice to cite both.
- **JSON-LD:** `codemeta:referencePublication` with the URL as `@id`.
- **Search:** free-text tier T4.3 on the item's name; `reference_publication:"…"` and
  `publication:"…"` match the name by substring. Because the name is the URL, a search matches the DOI
  string, not the paper's title.

## Rubric: include / exclude

Apply to each candidate and to the incumbent value; stop at the first rule that fires, except that
rule 4 is tested before rule 3: when the project's guidance is a per-component citation list, rule 3
never selects a paper from it. Decide Fields 14 and 27 together.

1. **Not a publication → never Field 14.** Fires for a software deposit DOI, concept or version (a
   `CITATION` file that holds only a Zenodo DOI is citing the code — Fields 2 and 12), a dataset
   (Field 28) or a repository URL.
2. **Poster, talk, presentation or conference abstract → Field 27, not 14.** Even when its whole
   subject is this software: the field's role is the paper-of-record (the JOSS-paper role).
3. **The project's own citation guidance names one paper for the software → that paper.** Evidence:
   `CITATION.cff` `preferred-citation`; a README or docs "Citing", "How to cite" or "Acknowledging"
   section; a JOSS badge. The project's designation decides even when the paper, strictly, describes
   a core library the software is built around. When the guidance names several papers, Field 14
   takes the software paper (for example the JOSS article), or else the first listed, and the rest go
   to Field 27. The guidance must be this software's own: a citation request in vendored third-party
   code does not count.
4. **Per-component citation lists with no single paper for the package → empty.** Fires when the
   project deliberately asks users of each tool or product to cite a different set of papers.
   Promoting one would override that guidance; all the listed papers go to Field 27.
5. **A paper about the method, model, format or algorithm, or about a different product → not
   Field 14.** Fires for a paper the software implements or wraps but that does not describe this
   software (it may predate the code), and for a paper describing another package the software
   consumes or feeds. It goes to Field 27 when the project presents it as a reference for the
   software (Field 27 rule 4).
6. **No guidance, but a paper by the developers describes this software → that paper.** Fires for a
   peer-reviewed paper that names the software in its title or presents its code in a dedicated
   section, and to which the project's documentation or its authors point. A paper that describes this
   software together with sibling tools still qualifies.
7. **Nothing qualifies → empty, with the search recorded.** A project statement that no paper exists
   ("A paper citation does not yet exist") is evidence. Record Field 14 as "Not found" only after the
   checks under *Where to find it*.
8. **Incumbent.** Keep it when it passes rule 3 or 6. When it fails rules 1, 2 or 5, move it to the
   field it belongs in and clear or replace Field 14. Field 14 is static: a routine refresh does not
   re-derive it; a full refresh re-verifies it.
9. **Never in both fields.** The Field 14 paper is not also listed in Field 27 under any identifier
   (DOI, ADS URL, publisher URL); moving a paper into Field 14 removes its Field 27 entry.

## Ask the user only when

- Two or more papers each qualify under rule 6 and no project source prefers one.

Anything else is decided by the rubric. A case no rule covers is a rubric gap: ask, and report it as
one.

## Where to find it, and traps

**Sources, in priority order.** Reference Publication tends to be obvious when it exists:
- CITATION.cff file (`preferred-citation`)
- README recommendations for how to cite the package

DOIs (Persistent Identifier, Version PID, Reference Publication) may be in:
- CITATION.cff
- README badges
- Zenodo integration
- codemeta.json

Then the docs' citing/acknowledging page, a `paper/` or `joss_paper/` directory, links from the docs
to an article, and the literature (ADS/SciX full text and title search for the software's name; the
developers' publication lists). The routes and their controls are in
`../sources/extraction-sources.md` (*Literature sources*).

**Verification.**
- DOIs must be full URLs: `https://doi.org/10.XXXX/XXXXX` (Fields 2, 12, 14, 27, 28, 29, 30).
- Verify the DOI resolves, and read its title from Crossref (`https://api.crossref.org/works/<doi>`).
- Cross-check against CITATION.cff preferred-citation and README citation sections.
- For a field that a publication could supply (Fields 14, 25, 26, 27), check the paper's
  Acknowledgments and Data Availability Statement before concluding it isn't there.
- Check a paper before recording "Not found": read the article far enough to know whether it presents
  the software, not only whether it cites it.

**Traps.**
- **A stale bibliography entry.** A repository's `.bib` file can carry a wrong DOI for the very paper
  in question (one entry for the second paper of a series held the first paper's DOI). Take the DOI
  from the article itself and from the links the docs actually use; search by author and year, not
  only by identifier, before concluding absence.
- **Algorithm reference lists.** "The following papers are references for the algorithm" names the
  method's papers, not a paper describing this software.
- **An author's publication list** is not a source for this field: most papers there use data or
  methods, not the software.
- **Publisher 402/403** is usually bot-blocking, not a paywall; a browser renders the page. ADS/SciX
  needs no personal token (anonymous bootstrap); the ADS web interface may answer automated requests
  with a 405 "Human Verification" page even though the record exists — confirm through the ADS API.

## Payload and roundtrip notes

- Key `referencePublication`, a single URL string (not a list), validated as a URL. `null` or an
  empty string clears the field; the related item itself remains.
- The value binds an existing related item on the **exact** identifier, else creates one with the URL
  as both `identifier` and `name` (name capped at 128 characters, so the URL must be ≤128 characters;
  a longer URL passes validation and fails at the database write).
- **A related item keeps its type on reuse.** Rows are shared across Fields 14 and 27–30 and bind on
  the identifier alone, so a URL first created as software or a dataset stays typed that way (and is
  typed that way in JSON-LD) when reused here. Moving a URL between Fields 14, 27, 28, 29 and 30 does
  not retype it.
- Related item names are placeholders — the URL itself, or `UNKNOWN`, in which case the page shows
  the identifier as link text. They carry no citation text; never choose a value by its stored name.

## Worked examples

- **Paper II describes the code.** SAVIC's docs link Paper II four times as the authority for the
  code's output, and its Section 3.4 presents the SAVIC code. Rule 6 puts Paper II's DOI in Field 14;
  Paper I, the antecedent study, goes to Field 27, replacing the ADS URL of Paper II that Field 27
  held (rule 9).
- **Framework paper across three tools.** PyAuroraX has no citation guidance, but a Frontiers article
  by its developers names PyAuroraX in its title and describes it with two sibling tools. Rule 6
  records it here; Field 2 keeps the software's concept DOI, so the page carries both citations.
- **Algorithm papers only.** pyflct's docs list three papers as "references for the FLCT algorithm";
  none describes the Python wrapper. Rule 5 fires; Field 14 stays empty and two of them remain in
  Field 27.
- **Model paper with no DOI.** ReesAurora implements Sergienko and Ivanov (1993), which predates the
  code by decades and has no DOI. Rule 5 fires; the paper goes to Field 27 as an ADS permalink.
- **Designation beats scope.** Kamodo's README lists its JOSS paper first under "Citing Kamodo", even
  though that paper's repository link is the core library. Rule 3 fires and it is recorded here.
